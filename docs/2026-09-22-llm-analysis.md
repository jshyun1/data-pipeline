# 우리 LLM 기능의 현재 구조와 개선 방향 — 분석 (2026-09-22)

**왜**: 지금 LLM 기능은 «job 분석 · 로그 분석» 두 가지다. 앞으로는 (1) 오류에 대해 **포괄적인 설명이 아니라
바로 실행할 수 있는 조치**를 주고, (2) ETL · CDC 가 Airflow 와 어떻게 물려 도는지까지 **정확히 설명하고 심층
분석**하며, (3) 나아가 **ETL job · CDC 파이프라인 · 워크플로우 생성**까지 하려고 한다. 그러려면 지금 무엇이
적용돼 있고 무엇이 없는지부터 정리해야 한다.

이 문서는 **코드를 읽고 확인한 사실**과 그 위에서의 판단을 나눠 적는다. 판단에는 근거와 반대 근거를 같이 둔다.

---

## 1. 지금 적용돼 있는 기법 (조사 결과)

«RAG 가 없다»가 «기법이 없다»는 아니다. 확인해 보니 다음이 이미 들어가 있다.

| 기법 | 구현 위치 | 내용 |
|---|---|---|
| 결정론적 컨텍스트 주입 | `llm/context/*ContextCollector` 7종 | 대상 종류(CDC_PIPELINE · ETL_JOB · WORKFLOW · WORKFLOW_DRAFT · WORKFLOW_NODE · WORKFLOW_TASK · ETL_ASSISTANT)마다 **서버가 무엇을 보낼지 결정**한다. 화면은 id 와 화면에 보이는 오류만 보낸다 |
| 컨텍스트 예산 관리 | `llm/context/LlmContext.assemble()` | 구역마다 우선순위(오류 원문 > 정체 > 상세 > 이력). 한도를 넘으면 낮은 것부터 자르거나 뺀다. 입력 한도의 60%(`CONTEXT_SHARE`)를 대상 정보에, 나머지를 대화에 준다 |
| 대화 압축 | `llm/chat/ConversationFitter`, `llm/agent/ConversationSummarizer` | 오류 분석은 오래된 문답 쌍부터 버리고(대상 정보·첫 분석은 항상 유지), 속성창 질문은 **LLM 으로 요약해 이어 간다**. 요약 실패 시 버리기로 물러난다 |
| 출력 형식 고정 | `llm/agent/ErrorAnalysisAgent` | 첫 답은 «원인 추정 / 확인할 것 / 조치 방법 / 확신도» 네 구역 강제. 추가 질문은 자유 |
| 역할 지시문 공유 | `llm/agent/AgentPrompts` | 플랫폼 구조 설명 + 공통 규칙(모르면 모른다고, 비밀값 요구 금지, 되돌리기 어려운 조치는 영향과 함께) |
| 개인정보 마스킹 | `llm/context/SensitiveDataMasker` | 이메일 · 주민번호 · 카드 · 전화. **값을 지우지 않고 종류를 남긴다.** 주민번호는 앞 6자리 날짜 검사, 카드는 Luhn 검사를 통과해야 가린다(Kafka offset · epoch 가 통째로 가려지는 것을 막으려고) |
| 권한 게이트 + 감사 기록 | `llm/chat/LlmChatService`, `llm_usage_log` | 요청마다 대상 종류로 권한 재확인. 사용자 · 대상 · 모델 · 입력문자수 · 토큰 · 지연 · 상태 · 마스킹 여부를 남긴다 |
| 스트리밍 · 공급자 추상화 | `llm/client/LlmChatClient` | SSE 스트리밍, Anthropic · OpenAI · Gemini · OpenAI 호환(내부) 4종. 스트리밍을 무시하는 프록시도 흡수. 첫 응답 120초 · 전체 300초 워치독 |
| 질문 기반 선별(검색의 맹아) | `llm/context/EtlAssistantContextCollector` | 전체 현황은 요약으로, **질문 키워드에 걸린 job 만** 상세로 붙인다. 이미 일종의 검색이다 |
| 검증기 결과를 컨텍스트로 | `llm/context/WorkflowDraftContextCollector` | 저장 전 초안에 게시용 `WorkflowValidator` 를 돌려 그 결과를 LLM 에 넘긴다. «도구 결과 주입»의 사전 형태 |
| 프롬프트 회귀 테스트 | `llm/agent/*Test`, `ConversationFitterTest`, `LlmContextTest`, `SensitiveDataMaskerTest` | 프롬프트 조립 · 자르기 · 마스킹에 단위 테스트가 있다 |

### 없는 것

도구 호출(tool calling), JSON 스키마 강제 출력, 의미 기반 검색 · 임베딩, **평가셋**, 사용자 피드백 수집,
프롬프트 버전 관리, 응답 캐싱, 멀티스텝 에이전트 루프, few-shot 예시, 런북 지식베이스.

### 운영 제약

- 내부 모델(`OPENAI_COMPATIBLE`, gemma4)은 **토큰 과금이 없다.** 여러 번 왕복해도 비용이 늘지 않는다 - 늘어나는 것은 지연뿐이다.
- 실제 입력 한도는 설정값 기준 **60,000자**(`max_input_chars`, 미리보기 API 로 확인). 스키마 전체나 로그 전문을 통째로 넣는 방식은 여전히 불가능하다.
- gemma4 의 **tool calling · 구조화 출력 지원 여부는 아직 확인되지 않았다**(API 키 접근이 막혀 보류 중). 이후 설계의 갈림길이라 먼저 확인해야 한다.

## 2. 진단 — 왜 지금 답이 «포괄적»인가

프롬프트 문제가 아니라 **컨텍스트에 들어가는 재료** 문제다. 현재 오류 분석에 들어가는 것은 세 가지뿐이다.

1. 이번 오류 원문
2. 대상의 현재 구성(파이프라인 · job · 워크플로우 설계)
3. 최근 실행 이력

사람 전문가가 «직접적인 조치»를 낼 때 쓰는 재료 중 **둘이 빠져 있다.**

- **과거에 같은 오류를 어떻게 고쳤는지.** 우리 DB 에 조치 이력이 있다(알림 확인 · 해소, 파이프라인 제어 명령 이력,
  job run 이력). 그런데 컨텍스트에 한 줄도 들어가지 않는다.
- **지금 실제 상태를 확인한 결과.** 커넥터 상태 · 복제 슬롯 존재 · 타깃 테이블 스키마는 **우리 API 로 즉시 읽을 수 있다.**
  LLM 은 그걸 읽을 수단이 없어서 «확인할 것»으로 사람에게 되돌린다.

즉 지금은 «한 번의 스냅샷 → 한 번의 답변» 구조라, 근거가 모자라면 포괄적으로 답할 수밖에 없다. 프롬프트를
아무리 다듬어도 여기서 더 나아가지 않는다.

## 3. 목표별로 필요한 기법

### 3-1. 직접적인 해결 방안 (효과가 가장 크고 가장 싸다)

**(a) 오류 지문화(fingerprinting)**
스택트레이스 · 메시지에서 숫자 · id · 타임스탬프 · 경로를 정규화해 지문 해시를 만든다.
→ «이 오류는 지난 30일간 7번 발생했고, 마지막에는 ○○ 로 해결됐다»를 컨텍스트에 넣는다.
임베딩 없이 SQL 로 된다. 부수 효과로 대시보드에 «같은 오류 N건»을 묶어 보여줄 수 있다.

**(b) 조치 결과 피드백 루프**
실패 화면에 «이 방법으로 해결됨» 버튼 하나. 지문 ↔ 조치 ↔ 성공 여부가 쌓이면 그것이 곧 우리 런북이고,
다음 답변의 근거가 된다. **이것이 «RAG 데이터셋 구축»의 실질적인 정답**이다 - 외부 문서를 긁어모으는 것보다
우리 현장에서 실제로 통한 조치가 훨씬 정확하다.

**(c) 읽기 전용 도구 호출(ReAct 루프)**
화이트리스트로 5~8개만 연다: 커넥터/태스크 상태, 복제 슬롯 목록, 타깃 테이블 스키마, Airflow task 로그 재조회,
최근 run 통계, NiFi bulletin. LLM 이 «확인할 것»을 스스로 확인하고 확정적으로 답한다.
내부 모델은 과금이 없으므로 5~10회 왕복도 비용 문제가 없다(지연만 관리).
gemma4 가 tool calling 을 지원하지 않으면 **«조회 요청 JSON 을 뱉게 하고 서버가 실행한 뒤 다시 호출»** 패턴으로
같은 것을 만들 수 있다.

**(d) 조치를 구조화 출력으로**
`{action:"restart_connector", target:"sink-2-…", risk:"low", why:"…"}` 형태로 받아 화면 버튼으로 잇는다.
실행은 기존 권한 체계(`@RequirePermission`)와 기존 API 로만 한다. 되돌리기 어려운 조치는 사람 승인 필수.

### 3-2. JOB 분석 심층화 (ETL · CDC ↔ Airflow 연계)

**(e) 그래프 컨텍스트**
워크플로우 → 노드 → job → NiFi 프로세스 그룹 → 단계, CDC → 제어 DAG → 커넥터 → 토픽 의 관계를 명시적
그래프로 만들고 **질문에서 k-hop 만 잘라** 넣는다. `WorkflowGraphText` 가 이미 맹아다.

**(f) 점진적 공개(progressive disclosure)**
처음엔 요약만 주고, LLM 이 필요할 때 도구로 상세를 당겨온다. 입력 한도 60,000자 안에서 심층 분석을 하려면
이 방식 말고는 없다.

**(g) 질의 라우팅**
질문을 구성 설명 / 성능 / 실패 원인 / 영향 분석으로 분류해 수집기 조합을 바꾼다. 지금은 화면이 대상 종류를
고정하고 있어서 «이 job 을 고치면 무엇이 영향받나» 같은 질문에 약하다.

**(h) 수치의 요약 통계화**
실행 시간 추이 · 적재 건수 · CDC lag 을 원본이 아니라 통계(중앙값 · p95 · 추세)로 넣는다. 토큰도 아끼고
«느려졌다»를 근거 있게 말할 수 있다.

### 3-3. 생성 (ETL job · CDC 파이프라인 · 워크플로우)

방향은 2026-09-21 검토와 같다 - 자연어 → **중간표현(IR)** → 검증 → 결정론적 컴파일. 기법 이름을 붙이면:

- **구조화 출력 강제**(JSON 스키마). 미지원이면 스키마 프롬프트 + 파서 + 재시도.
- **검증 실패 자가 수정 루프**: `WorkflowValidator` · `SqlValidationService` · `CdcPrerequisiteService` 의
  한국어 오류 메시지를 그대로 되먹인다. 2~3회로 제한하고, 실패하면 초안 없이 이유만 보여준다.
- **few-shot**: 이미 있는 워크플로우 · job 에서 예시를 자동 추출한다.
- **드라이런 미리보기 + 사람 승인(HITL)**: 무엇이 만들어지는지 diff 를 보여준 뒤에만 적용.

이미 가진 것: `WorkflowCompiler`(→ Airflow DAG), `NifiClient.createInitialDbToDbFlow`/`createFileLoadFlow`(→ NiFi job),
`PipelineService`(→ Debezium · JDBC 커넥터). **결정론적 컴파일러는 세 종류 다 있다.** 새로 만들 것은 IR 과 그라운딩이다.

### 3-4. 품질을 증명하는 장치 (이게 없으면 위 전부가 도박)

- **평가셋**: 과거 실패 30~50건 + «정답 조치»를 정리해 두고, 프롬프트 · 모델을 바꿀 때마다 돌린다.
  없으면 좋아졌는지 나빠졌는지 알 수 없다. 3-1(b)의 피드백이 쌓이면 평가셋이 저절로 자란다.
- **프롬프트 버전 기록**: `llm_usage_log` 에 `prompt_version` 한 칸.
- **응답 캐싱**: 같은 지문 + 같은 컨텍스트 해시면 재사용(지연 절감).
- **관측 화면**: 사용 기록은 이미 쌓이고 있다. 토큰 · 지연 · 실패율 화면만 없다.

## 4. 의미 기반 탐색 · RAG 에 대한 판단

**초기에는 벡터 검색을 넣지 않는 것이 낫다.**

- 우리 데이터는 문서가 아니라 구조화된 레코드(job · 단계 · 커넥터 · run · 조치 이력)다. SQL + 지문 검색이
  임베딩보다 **정확하고 설명 가능**하다. «왜 이 사례를 근거로 들었나»를 운영자에게 보여줄 수 있다.
- 폐쇄망에 임베딩 모델과 벡터 저장소를 하나 더 들이는 운영 비용이 작지 않다.

임베딩이 실제로 값어치를 하는 시점은 둘이다.
1. 런북 · 위키 · 장애 보고서 같은 **자유 문서가 실제로 쌓였을 때**
2. 자연어 업무 용어 → 테이블 매핑을 **사전으로 감당 못 할 만큼** 대상이 커졌을 때

그때까지는 용어 사전 테이블(`etl_formula_help` 와 같은 패턴)로 충분하다.

## 5. 권하는 순서

| 단계 | 내용 | 규모 | 얻는 것 |
|---|---|---|---|
| 0 | gemma4 tool calling · 구조화 출력 지원 확인, 실입력 한도 재측정 | 반나절 | 이후 설계의 갈림길 |
| 1 | 오류 지문화 + 과거 조치 이력 컨텍스트 주입 + 「이 방법으로 해결됨」 버튼 | 2~3일 | **«포괄적 답변» 문제를 직접 해결**. 새 인프라 없이 우리 DB 만으로 됨 |
| 2 | 읽기 전용 도구 호출 루프(화이트리스트 5~8개) | 4~5일 | «확인할 것» → «확인했음». 조치가 확정적으로 바뀐다 |
| 3 | 평가셋 + `prompt_version` | 2일 | 이후 모든 개선을 측정 가능하게 |
| 4 | 그래프 컨텍스트 + 질의 라우팅 + 요약 통계 | 1주 | ETL · CDC · Airflow 연계 심층 분석 |
| 5 | 생성(IR + 검증 + 컴파일) - 워크플로우 → CDC → ETL job | 2주+ | 자연어로 만들기 |

1단계를 먼저 하는 이유: 새 인프라가 필요 없고, 사용자가 체감하는 변화가 가장 크며, 여기서 쌓인 데이터가
2 · 3단계의 재료가 된다.

## 6. 위험과 전제

- **자동 실행 금지.** 생성물과 조치는 사람이 한 번 승인한다. 되돌리기 어려운 것(슬롯 삭제 · offset 초기화 ·
  토픽 삭제)은 도구 화이트리스트에 넣지 않는다.
- **도구는 읽기 전용부터.** 쓰기 도구는 3단계(평가셋)가 선 뒤에 검토한다.
- **폐쇄망 전제.** 스키마 · 컬럼명 자체가 외부 모델로 나가는 것을 꺼리는 현장이 있다. 생성 · 심층 분석은
  내부 모델 전용 기능으로 두는 편이 안전하다.
- **메타 캐시 신선도.** 그라운딩에 캐시를 쓰면 «언제 기준인지»를 화면과 프롬프트 양쪽에 적는다.
- **지연.** 내부 모델은 과금이 없는 대신 느리다. 도구 왕복 횟수 상한(예: 6회)과 전체 시간 상한을 둔다.
