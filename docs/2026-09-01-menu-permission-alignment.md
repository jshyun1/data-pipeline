# 메뉴 ↔ 권한 정합 작업 (2026-09-01)

「메뉴가 있는 위치」와 「그 기능을 소유한 시스템」이 1:1이 아니어서 생긴 어긋남을 정리했다.

## 1. 왜 애매했나

권한은 **기능 기준 5개 시스템**(COMMON / NIFI / AIRFLOW / KAFKA / ADMIN)으로 나뉘는데,
메뉴는 **사용자가 찾기 쉬운 위치** 기준으로 배치돼 있다. 둘이 어긋나는 자리가 생긴다.

| 화면 위치 | 기능 소유 | 비고 |
|---|---|---|
| 설정 > 알림/발송 관리 | **ADMIN** | 화면은 「설정」인데 API 는 ADMIN |
| 설정 > 연결정보 | **KAFKA + NIFI** | CDC·ETL 이 함께 쓰는 공용 정보 |
| 워크플로우 > 스케줄링 | **NIFI** | 화면은 「워크플로우」인데 NiFi 플로우 발행 기능 |

**채택한 원칙(B안): 메뉴 위치와 무관하게 «기능을 소유한 시스템»으로 판정한다.**
대신 그것만으로는 그룹 표시가 이상해지는 곳에 **그룹 자체 요건**을 명시할 수 있게 했다.

## 2. 바꾼 것

### (1) 메뉴 게이팅 규칙 확장 — `AppLayout.tsx`

기존 규칙은 딱 하나였다: **자식이 하나라도 보이면 그룹도 보인다.**
여기에 두 가지를 더했다.

| 새 속성 | 뜻 | 쓰는 곳 |
|---|---|---|
| `anySystems: [...]` | 나열한 시스템 중 **하나라도** 권한이 있으면 보인다 | 연결정보(KAFKA 또는 NIFI) |
| `requireAny: [...]` | **그룹 자체**의 최소 요건. 통과 못 하면 보이는 자식이 있어도 그룹을 숨긴다 | 필요 시 |

권한이 아직 안 실린 순간에는 기존처럼 fail-open(전부 표시)이다. 실제 차단은 언제나 백엔드가 한다.

### (2) 「설정」 메뉴가 절대 안 숨겨지던 문제 — 해결

원인은 한 줄이었다.

```
{ path: "/settings", label: "알림/발송 관리", system: "COMMON", ... }   ← 이전
```

**모든 역할이 COMMON=1(읽기)을 갖고 있다.** 그래서 이 자식이 항상 보였고,
"자식이 하나라도 보이면 그룹도 보인다" 규칙에 따라 **「설정」 그룹이 절대 숨겨지지 않았다.**

게다가 실제 API 는 ADMIN 이라 **조회자가 메뉴를 눌러도 403** 이 나는 불일치까지 있었다.

```
{ path: "/settings", label: "알림/발송 관리", system: "ADMIN", ... }    ← 수정
```

한 줄로 두 문제가 함께 해결됐다 — 메뉴가 제대로 숨고, 403 불일치도 사라진다.

### (3) 연결정보 — 공용 정보로 재정의

연결정보는 CDC 하위가 아니라 **설정 하위**이고, **CDC(KAFKA)와 ETL(NIFI)이 함께 쓴다.**
한쪽 권한만 있어도 필요하므로 `anySystems` 로 바꿨다.

```
{ path: "/settings/connections", label: "연결정보", anySystems: ["KAFKA", "NIFI"], action: "READ" }
```

**결과:** ADMIN 권한이 없는 CDC 담당자에게는 「설정」 그룹 안에 **연결정보 하나만** 보인다.
계정·역할·감사·알림은 안 보인다. 아무 권한도 없으면 「설정」 자체가 사라진다.

### (4) 실시간 모니터링 — 트리거 기능 제한 (기존엔 무방비)

`AirflowDashboardPage` 에는 권한 검사가 **한 줄도 없었다.** 백엔드는 막지만 화면은 다 보여줘서,
읽기 전용 사용자가 눌러 본 뒤에야 403 을 만나는 상태였다.

`AIRFLOW` **쓰기** 기준으로 다음을 막았다.

| 위치 | 처리 |
|---|---|
| 트리 우클릭 메뉴 (ETL DAG / CDC 파이프라인 / 잡 목록) **3곳** | 「실행 설정」 항목을 **목록에서 제거** |
| 우측 속성창 「실행 설정」 버튼 **2곳** | **비활성** + "Airflow 쓰기 권한이 없습니다" 안내 |

「상세」와 「실행 이력」은 조회라서 그대로 둔다.

### (5) CDC 「파이프라인 신규 생성」 버튼 — 비활성 → 숨김

사이드바에서 「생성」 메뉴가 아예 사라지는 것과 규칙을 맞췄다. 할 수 없는 동작을 화면에 남기지 않는다.

```
쓰기 권한 없음        → 버튼 자체가 안 보임
쓰기 있음 + 연결정보 0 → 버튼은 보이되 비활성 + "연결정보가 최소 1개는 있어야 합니다"
```

「권한이 없다」와 「조건이 아직 안 됐다」는 성격이 달라서 표현을 나눴다.

### (6) `app_menu` 테이블 현행화 — `V57`

이 표는 **화면 렌더링에 안 쓰인다**(메뉴는 프런트가 갖고 있다). 그런데
**「역할별 메뉴 오버라이드」 기능이 이 표로 목록을 만들기 때문에**, 낡으면 관리자가
**존재하지 않는 메뉴에 권한을 주게 된다.**

어긋나 있던 것:
- 연결정보가 여전히 CDC 하위(`/cdc/connections`)
- 「AirFlow > 생성/관리」 (실제로는 「워크플로우 > 스케줄링·실시간 모니터링·관리」)
- 알림/발송 관리 메뉴가 **아예 없음**
- CDC 「생성」에 쓰기 요건(7)이 빠져 있음

16행을 실제 메뉴 19행으로 교체했다. 오버라이드 설정은 0건이라 안전하게 재작성했다.

## 3. 결과 — 역할별로 보이는 메뉴

| 메뉴 | ETL 관리자 | ETL 개발자 | ETL 조회자 |
|---|---|---|---|
| 대시보드 | ✅ | ✅ | ✅ |
| 워크플로우 > 스케줄링 | ✅ 편집 | ✅ 편집 | 👁 조회만 |
| 워크플로우 > 실시간 모니터링 | ✅ 실행 가능 | ✅ 실행 가능 | 👁 **실행 메뉴·버튼 없음** |
| ETL > 생성 | ✅ | ✅ | ❌ 메뉴 없음 |
| CDC > 생성 | ✅ | ✅ | ❌ 메뉴 없음 |
| CDC > 관리 (신규 생성 버튼) | ✅ | ✅ | 👁 **버튼 없음** |
| **설정** (그룹) | ✅ 전체 | 연결정보만 | 연결정보만 |
| 설정 > 계정/역할/감사/알림 | ✅ | ❌ | ❌ |

> ETL 개발자·조회자에게 「설정」 그룹이 보이는 것은 **연결정보 때문**이다.
> 연결정보가 CDC·ETL 공용 정보라 의도된 동작이다. ADMIN 항목은 보이지 않는다.

## 4. 스케줄링(워크플로우) 권한 분리

처음엔 「스케줄링은 NiFi 플로우를 발행하는 기능이니 `NIFI` 가 맞다」고 판단했는데,
**발행 코드를 직접 확인해 보니 틀렸다.** `WorkflowPublishService.publish()` 는 NiFi 에
아무것도 쓰지 않고 **Airflow Variable 을 갱신**한다.

```
스케줄링 화면에서 «게시»
   → Airflow Variable (etl_wf_index, etl_wf_spec__*)
   → airflow/dags/etl_workflows_dynamic.py (DAG 팩토리가 Variable 을 읽음)
   → Airflow DAG 생성 + 스케줄 활성화
```

코드 주석도 그대로 말한다 — *「게시해야만 DAG가 생긴다」*, *「index에서 빠지고 spec
Variable도 지워 다음 파싱 주기에 DAG가 사라진다」*.

다만 **절반은 NiFi 다.** 워크플로우 노드가 가리키는 대상은 NiFi 잡이다
(`spec.put("nifi_pg_id", job.getNifiPgId())`). 정리하면 **「그리는 건 NiFi, 돌리는 건 Airflow」**.

그래서 하나의 시스템으로 묶지 않고 **동작 성격대로 갈랐다.**

| 엔드포인트 | 이전 | 변경 | 이유 |
|---|---|---|---|
| 목록·상세·검증 | NIFI READ | 그대로 | 조회 |
| 생성·수정·삭제·그래프 저장 | NIFI WRITE | 그대로 | NiFi 잡을 엮는 **설계** |
| **게시 / 게시 취소** | NIFI WRITE | **AIRFLOW WRITE** | DAG 생성·삭제 = **운영 반영** |

프런트도 같은 기준으로 나눴다 — 캔버스의 「게시」·「게시 취소」와 목록의 「게시 취소」는
`can("AIRFLOW","WRITE")` 로, 나머지 편집 버튼은 기존대로 `can("NIFI","WRITE")` 로 본다.

**효과:** 「Airflow 읽기만 있으면 스케줄링도 조회만」 이 성립한다. 설계는 그리되
**운영에 올리는 것(게시)은 Airflow 권한**이 있어야 한다.

## 5. 남은 논점 — 읽기/쓰기 모델

이번 작업은 **메뉴 표시 정합**을 맞춘 것이고, 권한 모델 자체의 한계는 그대로다.

1. **쓰기 = 변경 + 실행이 묶여 있다.** 「실행은 되지만 수정은 안 되는」 운영자 역할을
   만들 수 없다. 비트에는 `EXECUTE=4` 가 따로 있는데 UI 가 0/1/7 만 만든다.
2. **객체 단위 권한이 없다.** 「이 사람은 DZ 그룹만」 같은 구분이 불가능하다(설계서 §4.4 범위 밖).

둘 다 이번 범위에서 다루지 않기로 했다.
