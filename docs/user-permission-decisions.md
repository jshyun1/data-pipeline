## D1. 사용자·권한 데이터 저장 위치 → **metadata-db 단독**

**결정 이유 (사용자)**
> 전부 metadata-db에 구성하자. 사내 MySQL은 다른 MSA 포털도 같이 사용하는 부분이라 우리 프로젝트만 단독으로 사용하기에는 무리가 있다.

**"전부"의 범위 = 계정까지 포함합니다.**

초안에서는 D1 안 B를 "권한만 우리 DB, `ST_USER`는 로그인 검증에 계속 사용"으로 제시했는데, 그 단서가 결정 이유와 맞지 않았습니다. `ST_USER`도 다른 시스템이 같이 쓰는 테이블이므로 **똑같이 제외**합니다.

**무엇이 어디에 사는가**

| 데이터 | 위치 |
|---|---|
| 계정·비밀번호 | **metadata-db `app_user`** (BCrypt) |
| 역할 | metadata-db `app_role` |
| 사용자→역할 | metadata-db `app_user_role` |
| 역할→시스템권한 | metadata-db `app_role_system_permission` |
| 메뉴 | metadata-db `app_menu`, `app_role_menu_override` |
| 감사 로그 | metadata-db `permission_audit_log` |
| 외부 MySQL `mydb` | **사용하지 않음** |

**파급효과 (좋은 쪽)**

- **외부 의존이 0**이 됩니다. Cerebro ETL 단독으로 완결됩니다.
- **상용 판매 패키지가 그대로 완성**됩니다. 고객사에 별도 계정 연동 작업이 필요 없습니다.
- 공유 DB의 스키마·데이터 변경에 영향받지 않습니다.
- D4(NiFi·Airflow 개인 계정) 동기화가 단순해집니다 — 계정 원장이 우리 DB 한 곳이라 "사용자 비활성화 → 두 시스템 반영"이 한 트랜잭션 안에서 끝납니다.

**파급효과 (감수할 것)**

- **계정 수명주기가 우리 책임**이 됩니다. 입사자 등록·퇴사자 정지를 Cerebro ETL 관리 화면에서 직접 해야 합니다.
- 회사 계정이 정지돼도 Cerebro ETL은 자동으로 알지 못합니다. 관리자가 `use_yn='N'`으로 바꿔야 합니다.
- 사용자는 회사 계정과 별개의 비밀번호를 갖게 됩니다(전환 직후에는 동일 — 아래 참조).

**삭제 대상**

| 항목 | 내용 |
|---|---|
| 코드 | `AccountLookupService.java`, `AccountDataSourceConfig.java` |
| 설정 | `.env`의 `ACCOUNT_DB_HOST/PORT/NAME/USER/PASSWORD`, `application.yml`의 `account-db:` 블록 |
| 의존성 | `mysql-connector-j` (다른 곳에서 안 쓰면) |

## D2. 외부 MySQL 사용 → **사용 안 함**

D1에 따라 자동 확정. 쓰기는 물론 **읽기도 하지 않습니다.** 연결 설정 자체를 제거합니다.

**전환 방법 — 사용자가 체감하지 못하게**

`ST_USER.USER_PW`와 `app_user.user_pw` **둘 다 BCrypt 해시**입니다. 따라서 해시를 그대로 복사하면 **사용자는 같은 아이디·비밀번호로 로그인**합니다.

```
1) Cerebro ETL을 실제로 쓸 인원만 선별 (전체 65건을 다 옮길 필요 없음)
2) ST_USER → app_user 1회 복사 (USER_ID, USER_NM, USER_PW, EMAIL, TEL_NO, USE_YN, USE_*_DTTM)
3) 로그인 로직을 app_user 기준으로 전환
4) 검증 후 MySQL 연결 설정 제거
```

이 작업은 P1에 포함되며, 실패 시 3)만 되돌리면 즉시 복구됩니다.

## D5. 자체 계정 관리 → **구현 (D1에 따라 자동 확정)**

계정 원장이 우리 DB가 되므로, 자체 계정 관리는 선택이 아니라 필연입니다.

| 기능 | 근거 |
|---|---|
| 계정 생성/수정/비활성화 | 관리 화면 (`/admin/users`) |
| 비밀번호 변경 (본인) | `app_user.user_pw` — V8에서 nullable로 비워둔 컬럼을 되살림 |
| 비밀번호 초기화 (관리자) | 위와 동일 |
| 로그인 5회 실패 시 잠금 | `app_user`에 `login_fail_count`, `locked_until` 추가. 참고 솔루션의 `tb_user.login_fail_count`/`block_time`과 같은 방식 |
| 비밀번호 정책 | 대소문자+숫자+특수문자 9~16자 (참고 솔루션과 동일 수준) |

`auth_source` 같은 분기 컬럼은 필요 없습니다 — 계정이 전부 로컬이기 때문입니다.

## D3. 권한 단계 → **2단계 (읽기/쓰기)**

| 화면 | 저장값 | 의미 |
|---|---|---|
| 아무것도 체크 안 함 | `0` | 권한 없음 |
| 읽기 ☑ | `1` | 조회만 |
| 읽기 ☑ 쓰기 ☑ | `7` | 조회 + 변경 + 실행 |

**"쓰기"에 실행이 포함됩니다.** 예: Kafka 쓰기 권한자는 파이프라인을 수정할 수도, 기동/정지할 수도 있습니다.

저장은 3비트 마스크(`1=READ, 2=WRITE, 4=EXECUTE`, 참고 솔루션과 동일 규칙)를 그대로 씁니다. 나중에 "조회+실행만 가능한 운영자"가 필요해지면 **마이그레이션 없이 화면에 체크박스 하나만 추가**하면 됩니다.

## D4. NiFi·Airflow 쓰기 차단 → **개인 계정 전환**

**결정 이유 (사용자)**
> 실제 차단력과 감사 추적이 가능해야 한다.

**실측으로 확인한 것 — 생각보다 현실적입니다**

NiFi 컨테이너 설정 확인 결과:

```properties
nifi.security.user.authorizer          = managed-authorizer      # ← 다중 사용자 인가가 이미 활성
nifi.security.user.login.identity.provider = single-user-provider   # ← 여기만 1인용
```

`authorizers.xml`에 `file-user-group-provider` + `file-access-policy-provider`가 이미 구성돼 있고 `users.xml`에 신원 3개가 들어 있습니다. **즉 "사용자별 정책"을 담을 그릇은 이미 있고, 부족한 건 "사람마다 다르게 로그인시키는 방법" 하나뿐입니다.**

Airflow는 `AIRFLOW__CORE__AUTH_MANAGER=FabAuthManager`라 `airflow users create`와 FAB 역할(Admin/Viewer)을 바로 씁니다.

**전환 방식**

nginx의 "고정 공유 자격증명 주입"을 "**요청마다 백엔드에 물어봐서 그 사용자의 자격증명을 주입**"으로 바꿉니다(`auth_request` + `auth_request_set`). 인가 판정과 자격증명 발급이 한 번의 서브요청으로 처리됩니다.

- NiFi: nginx가 클라이언트 인증서로 인증하고 `X-ProxiedEntitiesChain`으로 최종 사용자 신원을 주장 → NiFi가 그 사용자 정책 적용
- Airflow: 백엔드가 개인 FAB 계정을 만들고 사용자별 세션 쿠키를 발급·캐시

상세는 [설계서 7.7](user-permission-design.md#77--nifi--airflow-개인-계정-전환-d4).

**⚠️ 이 결정에 붙는 조건 3개**

1. **P5a 스파이크(0.5일) 선행 필수.** NiFi 2.2.0에서 `X-ProxiedEntitiesChain`이 기대대로 동작하는지 먼저 확인합니다. 안 되면 대안은 LDAP 서버 추가뿐인데, 그건 Keycloak을 뺀 이유와 충돌합니다. 그 시점에 D4를 재결정합니다.
2. **접속 형태 확인.** 이 화면이 다른 사이트의 iframe 안에서 열린다면 `SameSite=Lax` 세션 쿠키가 전송되지 않아 프록시 인가가 전부 실패합니다. `SameSite=None; Secure`가 필요한지 P5 전에 확인합니다.
3. **퇴사자 처리.** `app_user.use_yn='N'`으로 바꿀 때 NiFi·Airflow 계정도 함께 비활성화해야 합니다. D1 덕분에 이게 한 트랜잭션 안에서 끝납니다.

**얻는 것**

| | 전환 전 | 전환 후 |
|---|---|---|
| NiFi/Airflow 감사 로그 | 전부 공유 계정 | **실제 사용자 ID** |
| 조회자의 캔버스 편집 | 가능 | 거부 |
| 조회자의 DAG 트리거 | 가능 | 거부 |

## D6. 초기 역할 세트 → **최소 2개**

| role_id | 이름 | COMMON | NIFI | AIRFLOW | KAFKA | ADMIN |
|---|---|---|---|---|---|---|
| `ROLE_ETL_ADMIN` | ETL 관리자 | 1 | 7 | 7 | 7 | 7 |
| `ROLE_ETL_VIEWER` | ETL 조회자 | 1 | 1 | 1 | 1 | 0 |

D3=2단계와 잘 맞습니다. 2단계에서는 "운영자(조회+실행)"를 표현할 수 없는데, 역할을 2개만 두기로 했으므로 애초에 필요가 없습니다.

- 두 역할 모두 `built_in = true`로 심어 삭제·개명을 막습니다(운영 중 지워지면 전원이 권한을 잃습니다).
- 역할 추가는 관리 화면에서 언제든 가능합니다.
- **부트스트랩**: 계정 이관 시 지정한 관리자에게 `ROLE_ETL_ADMIN`을 자동 부여합니다. 이게 없으면 아무도 첫 권한을 줄 수 없습니다.

## 미결 — D7 (배포 분할)

15.5~17.5일치 작업을 몇 번에 나눠 배포할지. **테이블 설계에 영향이 없으므로 P1 착수를 막지 않습니다.**

가장 위험한 세 지점을 **서로 다른 배포로 분리**하는 것이 핵심입니다.

| 위험 지점 | 무엇이 깨질 수 있나 |
|---|---|
| P1 로그인 전환 | 아무도 로그인 못 함 |
| P4 API 인가 | Airflow DAG 401 → 운영 적재 중단 |
| P5b NiFi 개인 계정 | NiFi 접속 자체 불가 |

## 확정 조합으로 본 실행 계획

| 단계 | 내용 | 통과 조건 | 예상 |
|---|---|---|---|
| **P1** | `V21` 마이그레이션 + `authz` 패키지 + **계정 이관·로그인 전환** + `GET /api/authz/me` | 기존 사용자가 같은 비밀번호로 로그인, 화면 무영향 | 3일 |
| **P2** | 관리 화면 3개 (계정 / 역할·권한 / 사용자 역할 배정) | 계정 생성 → 역할 부여 → 로그인이 화면에서 완결 | 4일 |
| **P3** | 메뉴 동적화 + 라우트 가드 + 안내 페이지 | 조회자 로그인 시 `ETL 생성`·`설정` 메뉴가 사라짐 | 1일 |
| **P4** | 서비스 토큰 + API 인가 ★ | **DAG 정상 동작이 통과 조건**, 조회자 POST → 403 | 3일 |
| **P5a** | NiFi 프록시 인증 스파이크 | NiFi 로그에 개인 신원이 남는 것 확인 | 0.5일 |
| **P5b** | NiFi·Airflow 개인 계정 전환 | 조회자로 캔버스 편집 → 거부, 조회는 정상 | 5일 |
| **P6** | 감사 로그 + 조회 화면 | 권한 변경·거부가 전부 기록 | 1일 |

합계 약 17.5일.
