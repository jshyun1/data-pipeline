# CDC를 워크플로우로 실행하기 — 방안 분석

"CDC도 워크플로우 캔버스에서 설계해 실행 제어하자"는 제안을 검토한 문서다.
**채택 결정 전 검토용**이며, 아직 아무것도 구현하지 않았다.

전제로 나온 요구사항 하나 — **CDC 노드는 다른 노드와 연결되면 안 된다.** 연결이 불가능한
노드 하나만으로 실행되어야 한다.

---

## 1. 지금 CDC는 이미 DAG로 제어된다

파이프라인마다 제어 DAG가 하나씩 있다(`airflow/dags/kafka_pipelines_dynamic.py`).

```
kafka_pipeline_{id}_control     schedule=None (수동 전용), max_active_runs=2
  params: action ∈ {deploy, start, stop, monitor}

  apply_action → verify_action → verify_target_db_landing → monitor_cdc_runtime
                                                            (PythonSensor, 30초 reschedule)
```

- `apply_action` 이 `POST /api/pipelines/{id}/{action}` 을 부른다.
- `monitor` 는 커넥터를 건드리지 않고 **감시만 다시 붙인다**(감시 Run이 죽었을 때의 통로).
- `start` 실행은 센서가 마지막 leaf로 남아 **DAG Run을 RUNNING으로 유지**한다.
  별도의 `stop` 실행이 STOPPED를 만들면 그때 성공으로 끝난다.

즉 **실행 제어 자체는 이미 완성돼 있다.** 화면에서는 실시간 모니터링의 파이프라인 우클릭 →
「실행 설정」에서 네 가지 동작을 고른다.

## 2. ETL과 CDC는 DAG Run의 의미가 다르다

| | ETL 워크플로우 | CDC 제어 |
|---|---|---|
| DAG Run 1회 | 배치 한 번 = 시작→끝 | **계속 떠 있음**(스트리밍 동안 RUNNING) |
| 끝나는 시점 | 마지막 태스크 완료 | 별도 `stop` 실행이 STOPPED를 만들 때 |
| 실행 지시 | 1가지(돌려라) | **4가지**(deploy/start/stop/monitor) |
| 순서 | 앞뒤 연결이 핵심 | 연결 개념이 없음 |

ETL 워크플로우의 `SUBWF` 노드는 `TriggerDagRunOperator(wait_for_completion=True)` 로
하위 DAG가 **끝나기를 기다린다**. CDC의 `start` 는 원래 끝나지 않으므로 이 방식이 성립하지 않는다.

## 3. 「연결 없는 노드 하나」가 곧 문제다

연결이 안 되는 노드 하나짜리 워크플로우라면, 워크플로우가 주는 것 중 남는 게 거의 없다.

```
순서 정의     연결이 없으니 무의미
선후행 조건   무의미
스케줄        CDC는 상시 스트리밍이라 "매일 14시 실행"이 어색
재시도        제어 DAG가 이미 자체 검증·재시도를 한다
```

**노드 하나 = 파이프라인 하나**면 지금의 「실행 설정」과 완전히 같다. 캔버스만 한 겹 씌운 셈이다.
여러 파이프라인을 늘어놓아 **한 번에 제어**할 때에야 비로소 새로운 가치가 생긴다.

## 4. 방안 셋

### A. CDC 노드 = 제어 DAG를 부르는 얇은 노드

`SUBWF` 가 하위 DAG를 띄우듯, CDC 노드도 `kafka_pipeline_{id}_control` 을
`conf={"action": ...}` 로 띄운다.

- **장점** 기존 제어 DAG를 그대로 재사용. 백엔드 변경이 가장 적다.
- **단점** `action` 을 어디서 정하나. 노드 속성에 박으면 "start 전용 워크플로우",
  "stop 전용 워크플로우"를 각각 만들어야 한다. 워크플로우 실행은 버튼 한 번인데
  CDC는 지시가 4개라 맞지 않는다.
- **함정** `wait_for_completion=True` 로 두면 `start` 는 영원히 끝나지 않는다.

### B. CDC 전용 워크플로우 종류를 둔다

워크플로우에 종류(`ETL` / `CDC`)를 두고, CDC 종류는 캔버스에서 **연결 불가 · CDC 노드만**
허용한다. 실행 시점에 action을 고른다.

```
워크플로우 종류 = CDC
  캔버스   CDC 노드만, 연결선 금지(검증 규칙 추가)
  실행     [배포] [시작] [중지] [감시 재개] 4개 버튼
           → 각 노드의 제어 DAG를 같은 action으로 동시 트리거
  스케줄   없음(수동 전용)
  완료판정 트리거까지만 책임진다(start는 원래 안 끝나는 실행)
```

- **장점** ETL과 섞이지 않는다. 여러 파이프라인의 **묶음 제어**가 가능해진다 —
  이것이 유일하게 새로 생기는 가치다.
- **단점** "워크플로우 종류"라는 개념이 새로 생기고 검증·컴파일러·화면이 갈라진다.

### C. 워크플로우가 아니라 「CDC 그룹 실행」으로 푼다

캔버스를 쓰지 않고, 이미 만들어 둔 **CDC 그룹**(예: `CDC_IMP`)에 실행 버튼을 단다.
"이 그룹의 파이프라인 전부 시작" 같은 식이다.

- **장점** 새 개념이 없다. 그룹은 이미 있고 화면 한 곳만 고치면 된다.
- **단점** "캔버스로 설계하자"는 원래 제안과는 형태가 다르다.

## 5. 판단

**묶음 제어가 진짜 목적이라면 C가 가장 싸고 정확하다.** 캔버스는 순서를 그리는 도구인데
CDC엔 순서가 없다. 연결이 안 되는 노드를 늘어놓은 캔버스는 결국 목록이고,
그 목록은 이미 트리로 존재한다.

그래도 캔버스로 가야 한다면 **B**. A는 action 문제를 풀 방법이 마땅치 않다.

## 6. 결정해야 할 것

이 기능으로 실제 하려는 일이 무엇인지가 갈림길이다.

| 하고 싶은 것 | 맞는 방안 |
|---|---|
| 여러 파이프라인을 한 번에 켜고 끈다 | **C** — 그룹 실행으로 충분 |
| ETL처럼 화면에 그려서 관리한다 | **B** |
| CDC와 ETL을 한 흐름에 엮는다<br>(CDC 정지 → ETL 적재 → CDC 재개) | 아래 참조 |

세 번째가 원래 제안의 의도였을 가능성이 있고, **실은 이것이 가장 쓸모 있을 수 있다.**
다만 이 경우 "CDC 노드는 연결되면 안 된다"는 전제와 정면으로 어긋나므로 먼저 정리가 필요하다.
연결을 허용한다면 A·B가 아니라 네 번째 설계(ETL 워크플로우 안에서 CDC를 한 단계로 취급)를
따로 검토해야 한다.

## 7. 지금 반영돼 있는 것

- 설계 화면 팔레트에 **CDC 트리를 보이게만** 해 두었다(관리 화면과 같은 계층).
- 클릭해도 캔버스에 얹히지 않는다. 노드 종류가 `JOB`·`SUBWF` 둘뿐이라 얹으면 저장은 되고
  **게시가 깨진다.** 화면에도 "아직 캔버스에 얹을 수 없습니다(목록 보기 전용)"로 적어 두었다.
