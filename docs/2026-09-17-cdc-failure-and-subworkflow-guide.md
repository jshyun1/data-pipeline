# CDC 실패 정책 전환 · 하위 워크플로우 교착 대비 — 변경 내용과 화면 안내

2026-09-17 작업 정리. 무엇이 바뀌었는지, **알림은 어디서 보는지**, **싱크가 멈추면 무엇이 자동이고 무엇을 사람이 해야 하는지**,
**멈췄을 때 화면에서 어떻게 되살리는지**를 적는다. 설계 경위와 실측 기록은 [CDC 실패 정책 문서 9절](2026-09-09-cdc-error-policy-dlq.md#9-전환-결과-2026-09-17),
작업 기록은 WORK_LOG 38 · 39절.

## 1. 한눈에

| 작업 | 바뀐 것 | 사용자가 보는 변화 |
|---|---|---|
| CDC 실패 정책 전환 | CDC 테이블 싱크가 한 건이라도 거부되면 **멈춘다**(전에는 일부 오류를 DLQ 로 빼고 계속 감) | 멈추면 **알림**이 뜬다 · CDC 관리 «상세 › Connector» 에 실패 정책 표시와 **«싱크 설정 재적용»** 버튼 |

| Kafka 보존 기간 | 7일 → **14일** | 없음(멈춘 동안 밀린 데이터를 14일까지 보관) |
| DLQ 정리 | DLQ 조회 · 재처리 API, 테이블(V75) 삭제 | 없음(화면에는 이미 없었다) |

| 복구 수단 | 멈춘 파이프라인을 화면에서 되살릴 수 있다 | «실행 설정» 에 **«재시작 (Restart)»**, CDC 상세 Connector 탭에 **«이 한 건 건너뛰기»**, 멈춘 상태에서도 «배포» 가 된다 |

## 2. 알림은 어디서 보나

### 2-1. 화면

| 위치 | 내용 |
|---|---|
| **상단 헤더 종 아이콘** | 최근 7일 **미확인 알림 건수**가 빨간 배지로 뜬다(30초마다 갱신). 누르면 아래 «알림 이력» 으로 간다 |
| **설정 › 알림/발송 › 알림 이력** | 알림 목록 · 상태(발생 · 해소) · 확인(ack) 처리. 검색 · 기간 · 심각도로 거른다 |
| **대시보드 머리줄 «조치 대기열»** | 위험 · 경고 · 정보 건수 알약. 누르면 목록 팝업, 항목을 누르면 해당 화면(CDC 알림은 CDC 관리)으로 이동 |
| **설정 › 알림/발송 › 알림 규칙** | 규칙 켜기 · 끄기, 심각도 · 조건 수정 |
| **설정 › 알림/발송 › 수신자 · 발송 채널** | 이메일 · SMS 로 받을 사람과 채널 |

«알림/발송» 메뉴는 ADMIN 권한 메뉴다.

### 2-2. 이번 작업과 관련된 규칙

| 규칙 | 뜨는 경우 | 로컬 | 운영(MSA, 9/17 확인) |
|---|---|---|---|
| **커넥터 FAILED** (CRITICAL) | CDC 커넥터 또는 그 **태스크**가 FAILED | 켬 | 켜져 있음 |
| **서비스 응답 없음** (CRITICAL) | NiFi · Airflow 등 수집기가 연속 3회 실패 | 켬 | **꺼져 있음** — 켤지 결정 필요 |

알림 문구 예: **«zz-정책전환-시험 — Sink 태스크 FAILED»** (로컬 시험에서 멈춘 뒤 약 20초 안에 뜸)

- 멈춰 있는 동안 **30분마다 다시 알린다**(재알림 1800초)
- 정상으로 돌아오고 **300초가 지나면 자동으로 해소**된다

### 2-3. 이메일 · SMS 로도 받으려면

**로컬은 받는 사람이 없다** — 등록된 수신자 1명(차수봉)이 비활성이다. 지금은 화면(종 아이콘 · 알림 이력 · 조치 대기열)에만 뜬다.
받으려면 «설정 › 알림/발송 › 수신자» 에서 활성화한다. 운영은 활성 수신자가 2명이다.

## 3. «싱크 설정 재적용» 이란

### 3-1. 왜 필요한가

커넥터 설정은 **파이프라인을 배포(준비)한 시점에 굳는다.** 코드의 실패 정책을 «멈춤» 으로 바꿔도, 이미 등록된 커넥터는 **옛 설정(DLQ 로 빼고 계속)으로 계속 돈다.**
배포를 다시 하면 새 설정이 들어가지만 **소스 커넥터까지 멈추고** Oracle 캡처 조건 점검도 다시 돌아, 운영 중인 파이프라인에는 부담이 크다.

«싱크 설정 재적용» 은 **싱크 커넥터에만** 지금 설정을 다시 넣는 기능이다.

### 3-2. 어디서

**CDC › 관리 → 파이프라인 줄의 «상세» → «Connector» 탭** 맨 위

| 표시 | 뜻 |
|---|---|
| 파란 안내 «싱크 실패 정책: 멈춤» | 새 정책 적용됨. 할 일 없음 |
| 노란 경고 «싱크 실패 정책: 건너뛰고 계속 + DLQ» + «이 커넥터는 이전 정책으로 등록돼 있습니다» | **옛 정책**. 오른쪽 «싱크 설정 재적용» 을 누른다 |
| (로그 파이프라인) «건너뛰고 계속» | 로그 파이프라인의 정상 정책(아래 3-4) |

버튼은 CDC 쓰기 권한이 있어야 눌린다. 누르면 확인 창 → «적용».

### 3-3. 누르면 일어나는 일

- **소스 커넥터는 건드리지 않는다.** 원천 변경분은 계속 Kafka 에 쌓인다
- 싱크가 **실행 중**이면 태스크가 새 설정으로 잠깐 재시작되고, **마지막으로 적재한 위치부터** 이어 읽는다(유실 · 중복 없음 — 로컬 시험 확인)
- 싱크가 **멈춰 있으면** 설정만 바꾸고 **멈춘 채로 둔다**(실행 지시는 Airflow 만 한다는 원칙)
- 파이프라인 상태는 바뀌지 않는다. **CDC › 로그** 에 «싱크 설정 재적용» 줄이 남는다

**언제 쓰나** — 전환 전에 배포한 파이프라인에 **한 번씩**. 새로 만드는 파이프라인은 처음부터 새 정책이라 필요 없다.
로컬 2 · 3번은 적용해 두었다. 운영은 **14 · 15 · 22번**에 필요하다(6절).

### 3-4. 로그 파이프라인은 멈추지 않게 두었다

로그 파이프라인(Filebeat → 로그 테이블)은 거부된 줄을 **건너뛰고 계속** 적재한다(DLQ 만 뺐다). 긴 로그 한 줄 때문에 뒤따르는 모든 로그 적재가 멈추는 편이
더 해롭다고 판단했다. 건너뛴 줄은 Kafka Connect 로그에 남는다. 로그도 멈춤으로 바꾸려면 코드 한 줄이다(`JdbcSinkTemplate`).

## 4. 싱크가 멈추면 — 자동인 것과 사람이 할 일

### 4-1. 무엇이 멈추나

타깃 DB 가 거부한 건(컬럼 길이 초과 · 제약 위반 · 타입 불일치 · 접속 실패)이나 읽을 수 없는 메시지를 만나면 **싱크 태스크가 멈춘다.**
멈춘 건 뒤의 데이터도 적재되지 않고 Kafka 에서 기다린다. 소스는 계속 Kafka 에 쌓는다.

> 실측 참고 — DB 가 거부한 건은 **전환 전에도** 이렇게 멈추고 있었다(Debezium JDBC 싱크의 동작). 달라진 것은 두 가지다.
> 읽을 수 없는 메시지를 DLQ 로 조용히 빼던 것이 멈춤으로 바뀌었고, **멈춘 것을 알림이 잡게 됐다.**

### 4-2. 자동 / 사람

| | 자동? | 내용 |
|---|---|---|
| 알림 발생 | **자동** | 약 20초 안에 «○○ — Sink 태스크 FAILED» |
| 파이프라인 상태 FAILED 표시 | **자동** | 런타임 감시가 10초 간격 3회 확인 후 FAILED 로 바꾸고 CDC 로그에 «런타임 감시 · 실패» 를 남긴다 |
| 원인 파악 | 사람 | 아래 4-3 |
| 원인 수정(컬럼 확장 · 데이터 · 접속 등) | 사람 | 타깃 DB 등에서 |
| **재시작** | **사람** | **자동으로 재시작하지 않는다.** 고치지 않고 다시 돌리면 같은 건에서 또 멈추기 때문이다. 방법은 5절(화면에서 «실행 설정 → 재시작») |
| 재시작 후 적재 재개 | **자동** | **멈춘 건부터** 다시 들어온다 |
| 파이프라인 상태 복구(FAILED → DEPLOYED) | **자동** | 싱크가 다시 RUNNING 이 되면 런타임 감시가 되돌린다 |
| 알림 해소 | **자동** | 정상 300초 유지 후 |

### 4-3. 원인은 어디서 보나

| 위치 | 보이는 것 |
|---|---|
| **CDC › 로그** — 상태 «실패», 구분 «런타임 감시» 줄을 펼침 | «Sink 상태 불일치 … tasks=[FAILED] · 원인: …» 메시지. **«GPT 분석»** 버튼으로 원인 · 조치 안내 |
| **CDC › 관리 › 상세 › 운영 상태** | 저장 상태 · 실측 상태 · 최근 제어 메시지 |
| **CDC › 관리 › 상세 › Connector › «○○ · 설정/실행상태»** | 실행상태 JSON 의 `trace` — 예외 원문(예: `value too long for type character varying(5)`) |
| **워크플로우 › 로그** — CDC 파이프라인의 제어 실행 | 감시하던 «시작» 실행이 «FAILED 로 동기화됨» 으로 실패 |

## 5. 복구 — 화면에서 하는 방법

> 2026-09-17 저녁에 **복구 수단 3가지를 추가**했다(아래 7절의 제안을 그대로 만들었다). 그 전에는 멈춘 파이프라인을 화면에서 되살릴 수 없었다.

### 5-1. A. 고칠 수 있는 원인 — 고치고 «재시작»

타깃 컬럼 길이 · 제약 · 접속 같은 고칠 수 있는 원인은 **원인을 고친 뒤 재시작**하면 된다. **멈춘 건부터** 다시 들어온다.

```
워크플로우 › 로그 → 왼쪽 트리에서 그 CDC 파이프라인 → 우클릭(또는 상세) → «실행 설정»
  → «재시작 (Restart)» 선택 → 실행
```

- 멈춘 커넥터·태스크만 다시 띄운다. **잘 돌고 있는 소스는 건드리지 않는다**(이력에 «재시작: SINK / 그대로: SOURCE(정상)» 로 남는다)
- 일부러 멈춰 둔(중지 상태) 커넥터는 깨우지 않는다
- 재시작 뒤 실제로 RUNNING 이 됐는지 확인한다 — **원인을 안 고쳤으면 실패로 끝나고** 그 예외가 그대로 보인다
- 실행 대기(READY)·중지(STOPPED) 상태에서는 «재시작» 이 거절된다 — 그때는 «시작» 이 맞다

### 5-2. B. 배포로 다시 세우기

커넥터 설정 자체가 잘못돼 멈춘 경우(접속 정보 변경 등)에는 **«실행 설정 → 배포(Deploy)» → «시작(Start)»** 으로 다시 세운다.
전에는 멈춘 상태에서 배포가 «Kafka Connect가 실패 상태입니다» 로 거절됐는데, 이제 된다.

- 배포는 소스·싱크 설정을 **모두 새로 넣고 둘 다 멈춘다**(READY). 이어서 «시작» 을 해야 한다
- 멈춘 동안 Kafka 에 쌓인 것은 시작하면 이어서 적재되고, 그동안 소스 DB 에서 일어난 변경분도 소스가 다시 뜰 때 잡는다
  (소스 DB 의 redo/WAL 보존 기간 안이어야 한다)

### 5-3. C. 고칠 수 없는 한 건 — «멈춘 한 건 건너뛰기»

깨진 메시지처럼 원본을 고칠 수 없는 건은 재시작해도 같은 자리에서 또 멈춘다. 그 한 건만 넘긴다.

```
CDC › 관리 → 파이프라인 «상세» → «Connector» 탭
  → 빨간 «싱크가 멈춰 있습니다» 안내의 «이 한 건 건너뛰기»
  → 내용·원인 확인 → 사유 입력 → «건너뛰기»
```

화면에 나오는 것: 멈춘 위치(토픽 · 파티션 · 오프셋), 밀린 건수, **그 레코드의 내용**(개인정보 마스킹 · 길이 제한), 접었다 펴는 «멈춘 원인».

- **넘긴 건은 타깃에 들어가지 않는다**(되돌릴 수 없다). 필요하면 원본을 확인해 수동으로 넣는다
- **사유가 필수**다. 누가 · 언제 · 어느 위치를 · 왜 넘겼는지 CDC 로그 이력(«SKIP_RECORD»)에 남는다
- 넘긴 뒤 **자동으로 다시 띄운다** — 다음 건부터 이어서 적재된다
- 싱크가 실제로 멈춰 있을 때만 된다. 또 화면에서 본 위치와 실제 위치가 다르면 거절한다(그새 상황이 바뀐 것이므로)

### 5-4. API 로 하려면

화면 대신 직접 부를 수도 있다(CDC 쓰기 권한 필요).

```bash
TOKEN=$(curl -s -H "Content-Type: application/json" \
  -d '{"userId":"아이디","password":"비밀번호"}' http://<서버>:18086/api/auth/login \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['data']['token'])")

curl -s -X POST -H "Authorization: Bearer $TOKEN" http://<서버>:18086/api/pipelines/<id>/restart          # 재시작
curl -s -H "Authorization: Bearer $TOKEN" http://<서버>:18086/api/pipelines/<id>/sink-stuck               # 멈춘 위치 조회
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"topic":"...","partition":0,"offset":9,"reason":"..."}' \
  http://<서버>:18086/api/pipelines/<id>/sink-stuck/skip                                                   # 한 건 건너뛰기
```

응답이 **409 «rebalance was underway»** 면 Kafka Connect 가 재조정 중이다 — 잠시 뒤 다시 부른다.

## 6. 하위 워크플로우 교착 대비 — 화면에서 달라지는 것

### 6-1. 무엇이 문제였나

하위 워크플로우 노드는 자식 워크플로우가 끝날 때까지 기다린다. 전에는 기다리는 동안 **워커 슬롯(동시 실행 4칸)을 쥐고** 있어서, 상위 워크플로우가 여럿 겹치면
«상위는 자식을 기다리고, 자식은 슬롯이 없어 못 뜨는» **교착**이 날 수 있었다(시험에서 재현: 3분 넘게 멈춤). 이제 기다리는 동안 슬롯을 비우고 새 서비스
**트리거러(airflow-triggerer)** 가 자식 상태를 지켜본다(시험: 같은 조건에서 36초 만에 성공, 자식 실패는 상위까지 실패로 전파).

### 6-2. 화면

| 위치 | 변화 |
|---|---|
| **워크플로우 › 로그 · 로그2** — 하위 워크플로우 노드(예: total 의 wf_dz_com_daily) | 자식이 도는 동안 **«실행 중»**. 내부 상태는 `deferred` 인데, 전에는 이런 상태가 영문 그대로 회색으로 보였다. CDC 제어 실행의 감시 대기(`up_for_reschedule`)도 «실행 중» 으로 보인다 |
| **실패 로그 창** | 그대로. 하위 워크플로우 실패는 전처럼 하위 실행 안의 실패 원인까지 따라간다 |
| **대시보드 상태 점검** | Airflow 항목에 **«트리거러»** 가 추가로 보인다 |

실제 워크플로우로 도는 것은 **2026-09-17 10:30 정기 실행(total)이 처음**이다. 하위 노드가 «실행 중» → 성공으로 끝나는지 확인한다.

### 6-3. 운영 참고

- 트리거러 메모리 한도 640MB(평소 약 270MB). 384MB 에서는 헬스체크와 겹쳐 메모리 초과로 재시작됐다
- 트리거러도 dags 폴더를 마운트한다 — Docker 재시작 뒤 «빈 dags 폴더» 복구 명령에 **airflow-triggerer 를 함께** 넣는다

## 8. 운영(MSA) 반영 순서

1. **알림** — «서비스 응답 없음» 을 켤지 결정, 수신자 확인(«커넥터 FAILED» 는 이미 켜져 있음)
2. 백엔드 · 화면 배포 — V75 가 `dlq_replay_request` 를 지운다(운영 0건 확인)
3. `docker-compose.yml` 반영: `airflow-triggerer` 기동, `kafka` 재생성(보존 14일 — 잠깐 끊겼다 Connect 가 다시 붙는다, 디스크 여유 확인)
4. 파이프라인 **14 · 15 · 22** 각각 «CDC › 관리 › 상세 › Connector › 싱크 설정 재적용» → 파란 «멈춤» 표시 확인
5. 옛 `dlq.pipeline-*` 토픽 6개는 비었는지 확인 후 수동 삭제(파이프라인을 지울 때는 자동으로 지워진다)
6. 다음 정기 실행에서 하위 워크플로우 노드가 «실행 중» → 성공으로 끝나는지 확인
